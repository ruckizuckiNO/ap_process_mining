How predictable is the manual queue?

A machine-learning check of the routing at Initial validation for manual orders (ZNB1): can the fields in the event log predict whether an invoice goes to the manual control queue (CTRL1) or to the goods-receipt check (WAITGR)? The descriptive findings are in the separate report Why do ZNB1 invoices go to the manual queue?

13,289 invoices 45% CTRL1 8 fields 5-fold CV grouped by PO

Short answer

AUC 0.95

The main model predicts the road correctly for 89% of invoices on POs it has never seen, against 55% for always guessing WAITGR.

AUC 0.93

with the supplier alone. Without the supplier, all other fields together reach only 0.81. The supplier carries most of the signal.

AUC 0.69

at best for suppliers the model has never seen. The rule can't be inferred from value or timing; it has to be learned supplier by supplier.

Not a cause

A good prediction shows the decision is systematic. It doesn't show why. The actual rule needs the SAP configuration.

1Setup

Question. If the routing is a configured rule, the fields that drive it should predict it well. If it's random or depends on things outside the log, they won't. The model is a measuring tool for that question, not something to deploy.

Unit and target. One row per ZNB1 invoice (PO_ID × SAP_PO_No). Target = 1 if the invoice's first Initial validation routes it to CTRL1, 0 if to WAITGR. The 45% share of CTRL1 is balanced enough to use plain accuracy next to AUC.

Fields

FieldMeaningKnown at validation?
supplierSupplier (Supplier_ID)yes
log_valuePO value, log(NOK + 1)yes
amount_diffClearing vs invoice amount (relative)no
inv_posOrder of the invoice on its POyes
n_invNumber of invoices on the POno
monthMonth of validationyes
weekdayWeekday of validationyes
hourHour of validationyes

The SAP fields on the validation event itself (processing type, user, object code) are the same for every invoice, so they carry no information and are left out. amount_diff uses the clearing amount, which is only known after payment, and n_inv counts invoices that arrive later. Both are kept to measure the pattern, and a separate model without them shows that they don't matter (section 2). log_value is the PO total, which can also include later invoices.

Models. A logistic regression as a linear baseline, and scikit-learn's HistGradientBoostingClassifier (200 iterations, supplier as a categorical field) for non-linear patterns and interactions.

Validation. 5-fold cross-validation with folds grouped by PO. Invoices on the same PO almost always take the same road, so letting one PO's invoices sit in both training and test data would overstate the result. All numbers below are out-of-fold: each invoice is predicted by a model that never saw its PO.

Metrics. AUC (0.5 = coin flip, 1 = perfect ranking). Accuracy, precision (of the invoices predicted CTRL1, how many really went there), recall (of the CTRL1 invoices, how many were caught) and F1, all at a 0.5 threshold.

3Which fields matter?

Permutation importance: how much the AUC of the main model drops when one field is shuffled, averaged over the five folds. A large drop means the model relies on that field.

Drop-one check: the AUC when the model is retrained without a field. This catches fields that matter but overlap with others, which permutation importance can understate.

4Robustness

Unseen suppliers. Folds grouped by supplier, so every test supplier is new to the model. Time split. Trained on invoices validated before 1 October 2025 (5,045), tested on the later ones (8,244).

For a new supplier the routing can't be predicted well: AUC 0.69 without the supplier field and 0.54 with it (an unknown supplier code only confuses the model). Value, invoice order and timing don't add up to a general rule. That fits a setting stored per supplier or per PO, not a rule on the invoice amount.

The pattern holds over time (AUC 0.90 on the later months), so the supplier effect is stable, not a one-off.

5What this does and doesn't show

  • Prediction isn't explanation. The model shows that the routing follows the supplier. It doesn't show which setting causes it. Candidates (supplier master flags, POs not set up for matching against the goods receipt, tolerance limits) are in the drivers report.
  • The value is per PO, not per invoice, so a per-invoice amount limit can't be tested properly.
  • The population changes towards the end of the period (fewer, slower cases from October). The time split checks this but can't rule it out.
  • One model family, default settings. No hyperparameter tuning; the point is the size of the signal, not the best possible score.
